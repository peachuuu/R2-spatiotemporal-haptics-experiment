## 1. 系统目标与研究边界

R2（Spirit Ruins／月萤遗迹）是一个被试内的双条件游戏触觉实验系统。它在相同的视觉、音频、事件脚本、攻击序列和总刺激剂量下，比较：

- **BH**：基础触觉；
- **STH**：时空触觉。

参与者只会看到“条件 A／B”；系统内部保存真实条件映射。每个会话使用同一 `timelineSeed`、投射物序列和危险区序列，仅改变触觉条件。系统用于研究与原型验证；正式采集前仍须独立完成伦理、量表授权、硬件安全和设备验证。

## 3. 实验流程与需求

1. 基本信息：参与者编号、年龄、性别、触觉经验等最小必要资料。
2. 知情同意。
3. 阈值校准：8 个固定区域（左/右手掌、拇指食指、中指无名指、小指）逐区输入输出等级（0–180，与上位机一致）并确认；生产模式下经硬件连接真实下发到固件（§5.5.1），确认值存入会话，但不自动驱动游戏刺激输出。
4. 说明与练习。
5. 条件 A 游戏。
6. 条件 A 后问卷：HXI、PXI 节选、舒适／疼痛等。
7. 条件 B 游戏。
8. 条件 B 后问卷：HXI、PXI 节选、舒适／疼痛等。
9. 盲态事件级样本比较（9 个事件：每事件一张游戏画面截图；样本 A／B 可反复试听，触觉样本与对应音频经同一 PREPARE→COMMIT 门控共同起播、可随时停止；A/B 随机映射 STH/BH，评分与偏好按真实条件存储）。
10. 总体评估与开放访谈。
11. 导出全部数据。

正式模式不暴露真实条件、开发条件切换或任意事件跳转。开发模式允许条件预览和事件导航。两种条件的攻击顺序须一致；游戏时间线是事件唯一导演，玩家移动、跳跃和攻击始终由参与者控制。

## 4. 已实现功能（已在代码中核对）

### 4.1 流程、随机化与界面

- 基于平衡块的 AB／BA 条件顺序分配，并保存分配来源。
- 参与者仅见 A／B 标签；内部映射为 `baseline → BH`、`spatiotemporal → STH`。
- 条件页标题带操作员标记：`○`＝BH 基础触觉、`✦`＝STH 时空触觉（§5.6.1）；参与者无法解读，仅操作员可快速核对真实条件，标记不写入任何数据表。
- 目录、回退、干跑跳过、会话列表、保存退出与未完成会话恢复。
- 练习与正式游戏通过 iframe 嵌入；消息同时校验 origin、协议版本、sessionId 与 runId。
- 正式模式隐藏开发面板、重启控件和条件切换；游戏完成后才允许进入对应问卷。

### 4.2 游戏、时间线与触觉边界

- G01–G12 事件时间线、稳定事件编号、种子化攻击顺序、投射物与危险区战斗。
- 条件策略 BH／STH 与「事件 cue → 样本 ID」绑定表、文档提供的样本波形和基础触觉派生已实现（§5.5.2）；正式采集前仍须实物联调确认体感强度与安全上限。
- 已具备 Web Serial 硬件连接、双阶段 `PREPARE → COMMIT_AFTER` cue 协调、停止与故障安全状态机；实现细节见 §5.5，设备协议的唯一细则见 `serial-haptic-protocol.md`。
- 真实硬件异常不应自动降级为无触觉；干跑模式可明确使用无触觉模拟。

### 4.3 当前数据保存与导出

- R2 主系统把每次流程动作、问卷回答、校准、游戏事件、触觉 cue 与尝试状态写入浏览器本地 IndexedDB：`electrotactile-study`。
- 收到每条 `GAME_EVENT` 后，R2 以串行队列持久化，避免高频事件乱序写入。
- 每个条件重试新增 attempt，不覆盖旧 attempt；中断可标记为 `interrupted`。
- 每个投射物、危险区与宝箱功能试次另以不可覆盖的 `OBJECTIVE_TRIAL` 记录写入当前 attempt；其原始 `GAME_EVENT` 仍完整保留。重试会新建 attempt，不会覆盖先前记录。
- 完成页「导出全部数据」一次下载核心压缩包 `{编号}_{YYYYMMDD-HHmm}.zip`：`raw/`（会话 JSON、游戏事件、触觉 cue、审计）、`analysis/subjective.csv` 与 `qc/data-quality.csv`。另可单文件下载 JSON 或主观 CSV。
- 现有汇总与客观试次记录包含投射物命中／躲避、攻击开始至第一次跳跃、危险区最终受击边界的离开／停留时间、宝箱寻找时间、实际攻击顺序、输入方式与触觉 cue 诊断。

## 5. 本次实施的改造

### 5.0 游戏暂停与就地阈值校准（2026-08-30）

- 游戏内“事件结束后暂停”不会中断正在播放的音频、视觉或触觉 cue；当前事件完整结束后，角色停留在场景中，必须点“继续下一事件”才推进时间线。
- 条件游戏与最终样本评估页均提供“阈值校准”入口。弹窗复用右侧“硬件连接”已经持有的同一设备：打开时先发送安全 STOP，随后可按与校准页相同方式调节八个区域。
- 校准弹窗不选择、打开或关闭串口，也不自动恢复游戏或样本试听；完成调整后关闭弹窗，再由操作员明确继续事件或重新播放样本。

### 5.1 双重逐事件本地保存

在现有 R2 主记录之外，游戏本身新增独立 IndexedDB 写前日志。

```text
游戏产生事件
  → 先写游戏 IndexedDB
  → 发送 GAME_EVENT 给 R2
  → R2 写入实验主会话 IndexedDB
  → 导出时以 R2 主会话为准
```

游戏恢复或再次嵌入时，将未同步的已保存事件补传；R2 以稳定事件键去重。意外关闭时，已完成事件绝不覆盖；未完成条件尝试标记 `interrupted`，并保留诊断原因。浏览器主动清除站点数据仍会清空本地记录，因此每次会话结束必须执行数据导出。

### 5.2 完整游戏日志

每一条游戏日志都必须有：

- `session_id`、`run_id`、attempt ID、相对运行时间与记录时间；
- 隐藏实验条件、真实触觉条件（BH／STH）、显示条件（A／B）；
- 当前视觉可得性（如 full／limited／restore）及其必要参数；
- 时间线事件 ID、试次编号、空间参数和玩家位置；
- 输入设备及动作来源。

新增或补齐的原子日志包括：

- 时间线事件开始、结束和应急跳过；
- 宝箱提示音／视觉 cue 出现、找到宝箱并完成有效交互、宝箱开启；每条 `chest-found` 都保存阶段内试次编号、cue→有效 O 键的寻找时长、宝箱实际侧别/坐标和玩家起始位置；
- 投射物与危险区的出现、预警、命中、躲避／逃离与结算；
- 向左／向右移动的开始与停止、跳跃、交互；
- 硬件 cue 的请求、预备、计划起播、设备实际起播、完成或错误。

汇总表会补齐完成的宝箱试次数和平均 cue→交互时长，两类攻击的出现／命中／成功躲避数、条件与视觉可得性、应急跳过事件及质量标记。每个宝箱的单次寻找时长保存在 `game-events.csv` 的 `chest-found` 行；完整长表保留原子事件，后续分析可逐试次重算，而不是仅依赖汇总均值。

### 5.3 正式实验应急跳过

正式与开发游戏均提供“跳过当前事件”按钮。点击后须二次确认，不要求输入口令或理由；系统自动记录 `operator-emergency-skip`、当前 G 编号、视觉可得性、触觉条件与时间，停止当前事件并安全前进。该 attempt 标记为含应急干预，分析时可排除或做敏感性分析。该按钮不恢复开发模式的任意跳转和条件切换。

### 5.4 移除冲刺

冲刺不是本实验所需的行为变量，且会引入额外的无敌帧与速度差异，干扰投射物／危险区的躲避比较。因此本次会从游戏输入、物理状态、碰撞豁免、手柄／键盘说明、屏幕按钮、视觉样式和测试中完整移除冲刺。旧导出的历史记录仍按原样保留；新会话不再产生冲刺动作。

### 5.5 硬件触觉链路：校准电压控制、样本绑定与音画同步

以下三部分均已按代码实现；设备协议细则见 `D:\SpiritRuins-Experiment\web\docs\serial-haptic-protocol.md`。正式试验的 STH/BH 走真实硬件路径；干跑和无触觉（NONE）不等待触觉、按既有视听时间线自动播放。单游戏预览可选择 STH/BH/NONE：前两者由操作者显式连接并 ARM 真实设备后，使用同一 PREPARE→COMMIT 门控规则；NONE 无硬件输出。任何模式切换前先安全停止当前触觉事务。

#### 5.5.1 阈值校准电压控制（生产模式真实下发）

- **硬件连接**：整次 R2 会话中唯一持有 Web Serial 的持久 iframe（游戏源 3001，`?mode=serial-host&embedded=1&sessionId=…`），挂在 R2 步骤内容之外（`HardwareHostFrame.tsx`）——校准页与正式游戏 iframe 都不直接访问 `navigator.serial`。面板折叠只隐藏界面，**不会卸载 iframe 或释放串口**；因此已连接后不要用折叠面板来“断开”。操作员在连接页面选择串口、**ARM（解锁输出）**，可随时「立即停止」或断开；页面上报固件版本、样本表版本与 DRY_RUN 标记。
- **操作序列**：每个区域的「确定」＝ STOP（输出归零、全部电极高阻）→ 重新 ARM → `SET_CALIBRATION(regionIndex, 输出等级)` → 等待固件 `CALIBRATION_APPLIED`；「开始校准」＝先应用该区域等级再 `START_CALIBRATION`，刺激将持续到操作者点击“停止校准”、确认/切换区域、急停、真正离开校准页或发生固件故障。点击校准页「继续」时，若仍在校准脉冲中，系统会先 STOP，再确认 ARM 成功后才进入说明/游戏，避免把未 ARM 设备交给第一个 cue。校准日志写入、状态刷新和普通 React 重渲染**不会**发送 STOP；校准期间不受 10 秒命令静默看门狗自动停止。任一步失败显式报错，绝不假装成功；干跑模式使用纯模拟 Mock。
- **区域与数值**：8 区域 regionIndex 与上位机 `config.json` 的 mapping_groups 同序（`calibrationHardwareMap.ts`）；输出等级 0–180 与上位机一致（UI 与适配器双重校验）。物理电压轨为共享通道——拇/食、中/无名各共享一条，8 区域对应 8 条输出轨而非 10 条。物理电压换算未经验证前，UI 只显示「输出等级（0–180）」，不显示伏特。
- **存储边界**：确认后的输出等级与固件版本写入会话快照并导出，但**不自动驱动游戏刺激输出**——游戏 cue 播放使用固件样本表内的电压参数，校准值仅用于校准流程与记录。

#### 5.5.1a Arduino 单机预览与区域校准（开发调试，非正式试验）

- **适用范围**：此入口仅用于已烧录 `ENABLE_DEV_CLI=1` 的 `demo.ino` 台架/体验调试；正式试验仍只通过 R2 硬件连接和协议 v2 控制，二者不能同时占用同一串口。
- **安全操作**：Arduino 串口监视器设为 115200 baud、行尾“换行”。每次预览必须按 `v <1–180>` → `a` → 样本或校准命令；`0`/`q` 立即停止、输出归零并使全部电极高阻。
- **区域校准预览**：`k0` 左掌、`k1` 左拇食、`k2` 左中无名、`k3` 左小、`k4` 右掌、`k5` 右拇食、`k6` 右中无名、`k7` 右小；校准样本为 100 Hz、PW 100 μs，电极对与《触觉样本制作需求》一致。输入一次 `k` 后持续输出，直到输入 `0/q`、改选区域或发生故障，无需每 10 秒重发。`p`/`r` 分别是 `k0`/`k4` 的兼容别名。
- **样本预览编号**：`1` G01、`2` G02、`3` G03、`4` G04、`51/52` G05 左/右宝箱、`6` G06/G10 划棱、`71–74` G07/G11 飞行物、`79/80` 危险区 A（最左）快/慢、`75/76` B 快/慢、`77/78` C 快/慢、`81/82` D（最右）快/慢、`8` G08、`12` G12 烟花；`s` 查状态、`c` 查固件样本目录、`h` 重显菜单。
- **基础触觉（BH）单机预览编号**：在上述对应 STH 编号前加 `100`，即 `101–104`（G01–G04）、`151/152`（G05 左/右）、`106`（G06/G10 划棱）、`171–174`（飞行物）、`179/180`（危险区 A 快/慢）、`175/176`（B）、`177/178`（C）、`181/182`（D）、`108`（G08）、`112`（G12）。BH 固定使用双手掌非空间电极组，但复用同一事件的频率、时程、PN=3、50% 双相平衡和 PW 查表。
- **从 Arduino 切到游戏/实验前**：在监视器输入 `0` 或 `q`，确认收到停止提示后关闭串口监视器；同一物理串口不能被 Arduino 监视器、单游戏预览和 R2 正式硬件连接同时占用。

#### 5.5.1b 预览模式与正式模式：实际切换操作

1. **Arduino 单机样本预览**：上传启用 `ENABLE_DEV_CLI=1` 的固件，115200 baud、行尾“换行”；输入 `v <1–180>` → `a` → STH 或 BH 编号。用 `0/q` 停止，并关闭监视器后才可把设备交给浏览器。
2. **单游戏预览（用于验收触发规则）**：启动游戏项目并打开 `http://localhost:3001`；页面中选择“时空触觉模式”或“基础触觉模式”，点击“连接触觉设备并 ARM”，在浏览器串口授权框选择同一设备。随后从 G01 开始运行或用开发事件跳转核对音画触共同起播。切到“无触觉测试模式”仅验证音画/游戏流程，不触发硬件。
3. **退出单游戏预览**：先使用页面“停止并断开触觉设备”（它会 STOP 后释放 Web Serial），再关闭该预览页或切换到 NONE；之后才能打开 R2 正式系统占用同一设备。
4. **R2 正式试验**：启动 `http://localhost:5173`，按正式流程进入校准和条件游戏。条件由 R2 隐藏随机化决定，操作员不在游戏页手动选择 STH/BH；由持久 HardwareHost iframe 选择串口并 ARM。正式 STH/BH cue 必须完成 PREPARE 后才共同起播，失败会暂停并显示可恢复错误，绝不自动降级为无触觉。

   - **必须先选“生产”模式**：步骤 1「基本信息」中的“干跑（仅模拟）”无论硬件连接是否已建立/ARM，校准均使用 Mock、游戏也不会向设备发送真实触觉 cue；页面出现“干跑 / 仅模拟”徽章即代表不可能有电刺激。用于真实硬件体验或正式采集时，请从会话入口新建会话并选择“生产”。
  - 进入条件游戏前，展开右侧「硬件连接」，确认显示“已连接 · 已 ARM”，再开始游戏。校准页「继续」现在会自动完成必要的 STOP→ARM 交接；硬件连接在**所有已连接状态**（未 ARM、已 ARM、UI 尚显示忙碌、等待玩家交互或样本播放期间）每 5 秒发送一次无刺激 `GET_STATUS` 心跳。心跳不可重入，不会在前一次状态查询尚未结束时继续堆积，因此既能让 30 秒固件看门狗保持 ARM，也不会让排队心跳堵住后续 cue。主动点“立即停止”或断开仍会撤 ARM，之后须在连接页面手动点击 **ARM**。

#### 5.5.3 触觉与音频、动画的同步（两阶段共同起播点）

- **单一时钟**：游戏内全部音频与动画都由事件内经过毫秒（`eventElapsedMs`）驱动，该时钟可在 cue 边界冻结与平移。每次 cue 的运行时去重键为“实际时间线事件 ID + cue 名”（如 `G07-P03:projectile`、`G07-CHEST01:chest-cue`），而非只按 cue 类型去重；因此 G05/G09、G06/G10、G07/G11 攻击及每个新增宝箱都会各自请求一次触觉。
- **正式 STH/BH 试次**（`hapticGate` 开启）：cue 到期瞬间游戏时钟冻结在 cue 边界，向 R2 发 `CUE_REQUEST(cueKey, baseSampleId)`，等待 R2 的 `START_CUE`。单游戏预览的 STH/BH 采用同一冻结语义，但由本页真实 Web Serial 主机直接完成 PREPARE→COMMIT；干跑/NONE 不冻结。
- **R2 编排**（`ConditionScreen` → `cueOrchestrator`）：解析样本 ID → 经硬件连接下发 `PREPARE_SAMPLE` → 收到 `PREPARED`（样本存在、电极合法互斥、参数校验通过、输出未开启）→ 在 R2 页选定未来共同起播点 `cueAt = now + leadMs`（默认 150 ms）→ 向固件发 `COMMIT_AFTER(相对 delayMs)`（设备以自身 tick 起播并回报 `STARTED/deviceStartUs`）。R2 保留 `cueAt` 仅用于本页调度和日志；向游戏 iframe 发消息前，改算为剩余 `START_CUE(delayMs)`。
- **对齐方式**：父页和跨源游戏 iframe 的 `performance.now()` 不保证使用同一 time origin，因此绝不把父页绝对 `cueAt` 传给游戏。游戏在 cue 边界冻结，用自身时钟等待 `delayMs` 后从原边界解冻；MCU 同样只收相对延迟。迟到或重复的 `START_CUE` 在游戏未冻结时会被忽略。触觉、音频、动画共享同一共同起播点。系统不声称亚毫秒精度；实际同步偏差、设备起播时刻与各阶段时间戳写入逐 cue 日志（`haptic-cues.csv`）。
- **失败门控与恢复跳过**：未连接硬件、未 ARM、PREPARE 超时、样本未定义或硬件错误 → 冻结在该 cue，正式试次**绝不自动降级为无触觉**。G01 的机关音画受第一个 cue 边界门控：未取得共同起播许可时保持等待态，不会出现音画先播放而触觉失败的假同步。其他事件只在**自己的** cue 边界冻结；例如 G02 的坠落前置音画仍会在 t=0 正常播放，不能被其 t=5.167 s 的石块 cue 提前阻断。操作员可在游戏内点“跳过当前事件”→“确认跳过”：R2 会先收到已认证的恢复请求并查询真实设备；仅当状态为 **已连接、已 ARM、无故障且 `ARMED_IDLE`** 时，才清除旧错误、记录 `operator-emergency-skip` 质量标记、解除冻结并进入下一事件。未连接、未 ARM、故障或 `PREPARED/SCHEDULED/PLAYING` 状态一律保持冻结并说明原因；系统不会自动 ARM，也不会在可能仍有输出时跳过。
- **串口事务与失联恢复**：同一硬件连接的普通协议命令（心跳 `GET_STATUS`、校准、`PREPARE_SAMPLE`、`COMMIT_AFTER`）严格串行，避免心跳与 cue 竞争同一个 MCU 串口状态；`STOP` 仍可越过队列抢占。连接页同时监听浏览器原生 COM 设备断开事件；若浏览器读取流已结束，即使尚未发出下一条 cue，也会立即（原生事件）或最迟在下一次 5 秒 `GET_STATUS` 心跳时标记失联、释放 reader/writer lock 并关闭旧端口。端口打开后 `HELLO` 最多自动尝试 3 次，以覆盖 RP2 Nano 的 USB CDC 启动稳定窗口；每一次关闭和新建连接都会清空二进制帧解码缓存，避免 USB 恰在帧中断开后，旧半帧吞掉下一次 `HELLO/ARM` 响应。单次 `TIMEOUT` 不再立即销毁仍可用的 COM 句柄，连续 3 次通信超时才释放；明确的 `IO`、`NOT_CONNECTED` 或浏览器断开事件仍立即释放。`ARM` 回包若丢失，宿主会用 `GET_STATUS` 核验设备实际 ARM 状态，避免“设备已 ARM、网页却报 ARM 失败”；`BUSY`、`NOT_ARMED`、样本未定义等有效设备拒绝不会误判为断线。R2 外层 ARM、校准和 PREPARE 等待窗口统一放宽到 7 秒，长于硬件宿主自身处理窗口，防止父页面在真实结果返回前先行报错。连接页以递增连接代号隔离异步回包：旧连接的迟到回包不能把面板重新写成“已连接/已 ARM”，也不会影响已经重新选择的端口。重新选择 COM5 后仍必须由操作者手动 ARM；系统绝不在断线恢复后自动解锁输出。
- **安全状态机**：`CONNECTED_SAFE → ARMED_IDLE → PREPARING → PREPARED → SCHEDULED → PLAYING`；任意 STOP、超时、故障或看门狗 → 输出 0 + 全部电极高阻；ARM 须操作员手势，页面加载不自动 ARM。

#### 5.5.7 游戏内就地调级（暂停后调阈值）与连接机制保护（2026-08-30）

- **触发场景**：被试在正式游戏中途报告某区域体感不适/过弱，操作员在条件页点「调整输出等级」。系统请求游戏在当前事件结束后暂停（`pauseAfterEventToken`），并打开与校准页相同的 8 区面板。
- **就地调级（不 STOP）**：游戏内面板的「确定」走 `applyVoltageInPlace`——先查设备状态，**已 ARM 且空闲（ARMED_IDLE）时直接下发 `SET_CALIBRATION`**；设备正在播放/调度时显式提示“设备正在播放触觉，请等当前事件结束后重试”，绝不发 STOP、绝不掐断当前触觉、绝不断开硬件连接。脉冲预览同样先就地应用等级；停止预览后自动重新 ARM（`stopStimulationInPlace`：STOP → ARM），把已解锁设备交回游戏。校准页与对比页/终评页仍使用原 STOP 流程（那些页面停脉冲是正确动作）。
- **推荐操作顺序**：① 先点「事件结束后暂停」，等游戏完全停住；② 再在面板中调整并「确定」；③ 关闭面板继续游戏。即使未等停稳就点「确定」，也只会收到“设备忙，请稍候”提示，连接不受影响。
- **区域等级注意**：8 区等级存于固件内存，设备断电/重插/重连会清零；复位后必须重做 8 区校准，否则未校准区域回退到全局最后等级。中途调级频率低（仅被试报告不适时），重连后按操作纪律重校准即可。

> ⚠️ **不要更改硬件与网页连接机制。** 以下连接行为已通过真机逐命令诊断、连续 40 次状态查询与两端全量测试验证，是当前稳定性的基石：
> ① 固件 `SERIAL_DEBUG=0`（串口只承载二进制协议帧，禁止任何调试文字）；② 打开端口必须置位 DTR/RTS；③ HELLO 最多自动重试 3 次（覆盖 USB CDC 复位窗口）；④ 5 秒不可重入 `GET_STATUS` 心跳（维持 30 秒固件命令看门狗）；⑤ 单次 TIMEOUT 容忍、连续 3 次才释放串口，IO/断开立即释放；⑥ connectionEpoch 隔离迟到回包；⑦ 断线后必须手动重连 + 手动 ARM，绝不自动解锁输出；⑧ STOP 后保留最后校准等级（固件不归零）；⑨ 样本播放按电极所属区域取校准等级（未校准回退全局）。任何对上述机制的改动必须先跑 `scripts/diagnose-haptic.ps1` 真机验证，再跑两端全量测试与 E2E，全绿方可合入。

- 播放交互复用样本对比的安全逻辑：PREPARE 成功后才共同起播；准备中显示 `…` /「准备中」，播放中显示 `■` /「播放中：雨声 + 触觉」，可点停止；播放结束自动复位。同一时间只允许一张卡播放；干跑、未连接或未 ARM 时禁用并说明原因；离开最终评估页时安全停止。
- 游戏内所有宝箱紫色圆点（G05、G09、G07/G11 新增 CHEST）统一使用低视野 G05 的弱呼吸样式，避免阶段间提示显著性不一致。

## 6. 客观试次、导出物与分析用途

### 6.1 客观试次定义

游戏只被动记录，不读取这些记录来改变角色移动、碰撞、时间线、问卷、条件或触觉调度。每一功能试次都有稳定的 `trial_uid`；同一试次的一个或多个触觉 cue 在 `haptic-cues.csv` 通过该字段关联。

- **投射物**：`firstJumpRtMs` 是攻击开始到第一次跳跃输入；没有跳跃则为空，不用其他动作替代。
- **危险区**：`areaExitMs` 与 `dwellTimeMs` 按游戏现有的最终受击边界计算，不按视觉扩张范围另设规则。
- **宝箱**：对 G05、G07-CHEST01–03、G09、G11-CHEST01–03，`completionTimeMs` 统一为**宝箱提示音实际起播时刻** `audioOnsetMs` 到首次有效且成功交互时刻 `interactionTimeMs` 的差值；三项毫秒值均保留在原始 `objective-trial.metrics_json`，并作为 `objective-trials.csv` 的明确列导出。该被动记录不改变提示音、动画、触觉或交互门槛。
- **无效技术试次**：`trial_valid=0`、`success` 为空，`invalid_reason` 为硬件故障、操作员跳过、运行中断或游戏错误之一；这不等价于行为失败（`success=0`）。

一个完整参与者在两个视觉可得性阶段的四个 stage×visibility 单元中，计划记录 `16` 个投射物、`8` 个危险区和 `4` 个宝箱，共 `112` 个有效功能试次。`qc/data-quality.csv` 按真实触觉条件分别列出计划、有效、无效与缺失数。

### 6.2 核心压缩包

「导出全部数据」下载 `{编号}_{实验开始时间}.zip`（`YYYYMMDD-HHmm`，不含昵称）。压缩包只含原始、主观和质量控制资料；不含派生表或量表对照表。

| 文件 | 粒度 | 用途 |
|---|---|---|
| `raw/*_session.json` | 完整会话 | 原始归档、恢复与审计（含问卷呈现顺序与每次 attempt） |
| `raw/*_game-events.csv` | 每个游戏原子事件一行 | 保留的逐事件原始日志；`objective-trial` 行带 `trial_uid` |
| `raw/*_haptic-cues.csv` | 每个触觉 cue 一行 | 同步偏差、样本、设备故障与关联的 `trial_uid` |
| `raw/*_audit-log.csv` | 每个流程操作一行 | 同意、导航、跳过、中断、导出与操作审计 |
| `analysis/*_subjective.csv` | 每题一行 | 原始主观回答长表（人口学、HXI、PXI、舒适／疼痛、比较与访谈） |
| `analysis/*_objective-summary.csv` | 参与者×真实触觉×视觉可得性 | 正式分析直接使用的四行客观汇总：BH/limited、BH/full、STH/limited、STH/full；包含投射物、危险区、宝箱与四个宝箱完成时长 |
| `analysis/*_subjective.xlsx` | 一位参与者一个工作簿 | `Participant`（1 行）、`ConditionSurvey`（BH/STH 各 1 行）、`Suitability`（9 行）、`FinalEvaluation`（1 行）、`Interview`（1 行） |
| `qc/*_data-quality.csv` | 条件×stage×visibility×类型 | 每个计划单元的有效、无效和缺失计数 |

### 6.3 导出与会后整理

1. 在完成页下载并妥善备份核心 ZIP。
2. 在 `D:\R2\experiment-system` 运行：`npm run derive:data -- "C:\下载目录\P001_YYYYMMDD-HHmm.zip"`。
3. 日常分析直接使用 ZIP 内的 `analysis/*_objective-summary.csv` 和 `analysis/*_subjective.xlsx`；它们均由已持久化的正式运行结果和问卷答案生成，不从动作日志反推。原始 ZIP 必须同时保留以便追溯。
4. 如需更细粒度或跨被试派生表，再运行 `npm run derive:data -- "C:\下载目录\P001_YYYYMMDD-HHmm.zip"`；系统会在 `D:\R2\experiment-system\derived\` 写出 `objective-trials`、`hxi`、`pxi` 和 `game-summary` 四张 CSV。

`objective-summary.csv` 的 `projectile_total`、`area_total`、`chest_total` 只计入对应已完成正式 attempt 的有效功能试次；`success_rate=success/total`，无有效试次则留空。完整正式会话每一行应分别有 16 个投射物、8 个危险区、4 个宝箱。`chest_1_completion_ms` 至 `chest_4_completion_ms` 仅写成功找到的宝箱；均值和中位数只基于这些非空完成时长。`condition_order_position` 是该真实触觉条件在 A/B 运行顺序中的位置（1 或 2）。

`subjective.xlsx` 不重算量表，也不还原或修改回答：`ConditionSurvey` 保留 HXI 20 题、PXI 6 题、舒适度与疼痛原始分；`Suitability` 保留九事件的真实 STH/BH 评分、偏好、理由以及可选 A/B 盲态映射；`FinalEvaluation` 同时保留显示偏好和对应的真实 BH/STH/none；`Interview` 按既有访谈题 ID 作为列保存原文答案。

命令会验证 ZIP 是否含所有核心文件；缺失时停止并明确指出缺少的文件。每张派生表都带 `schema_version` 与 `reference_version`。静态数据字典和量表键位于 `D:\R2\experiment-system\references\`（`data-dictionary-v1.csv`、`hxi-key-v1.csv`、`pxi-key-v1.csv`），不随被试文件重复下载。

访谈与其他问卷答案都在 `analysis/*_subjective.csv` 的逐题行中；完成页导出前会话刷新后仍从 IndexedDB 读取同一份会话数据。

事件试次嵌套于参与者，统计分析不应把每条事件当作独立参与者。使用条件、视觉可得性、事件类型及其交互项时，应保留 participant/session 的随机效应或相应的重复测量结构。
